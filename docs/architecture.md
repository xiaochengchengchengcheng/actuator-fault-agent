# 系统架构说明

## 目标

系统服务于机电执行器从零件加工、电机制造、电子装配、总成装配到下线测试的故障定位。它既可以由工程师提问触发，也可以由产线报警或故障检测装置主动触发。它解决的不是开放域问答，而是把“报警、现象、型号、工位、测量、工艺知识、历史案例”组织成可复核的诊断证据链。

## 为什么采用显式状态图

工业诊断同时包含确定性逻辑和概率性推理。自由循环型 Agent 容易隐藏路径，也难以规定哪些判断必须人工确认。因此主流程直接使用 LangGraph `StateGraph`：节点只做一类工作，边负责路由，checkpointer 保存线程状态，`interrupt()` 承担高风险人工复核。

LangChain 在图内负责三件事：统一模型接口、工具定义和 Pydantic 结构化输出。系统没有把所有工具一次性交给模型；读取测量、检索知识等关键动作由图确定顺序，模型只在证据汇总阶段选择和排序候选原因。

## 节点职责

| 节点 | 输入 | 输出 | 失败策略 |
|---|---|---|---|
| validate_input | 原始问题、执行器和工位 | 标准化诊断上下文 | 缺少关键标识时返回待补数据 |
| retrieve_baseline_knowledge | 问题、报警码与标识 | 型号标准和基础故障知识 | 无命中时保留空证据并降级 |
| load_measurements | 执行器 ID | 只读测量快照 | 数据源不可用时进入证据不足路径 |
| rule_screening | 测量、阈值 | 确定性告警和候选原因 | 纯函数，可独立测试 |
| build_diagnostic_query | 报警、测量与规则命中 | 数据增强检索语句 | 原始数据保留在状态中 |
| retrieve_diagnostic_knowledge | 数据增强检索语句 | 对应排查章节和历史案例 | 与基础检索结果去重合并 |
| synthesize | 全部原始证据 | 结构化诊断草案 | 模型失败时回退规则报告 |
| risk_gate | 草案、告警、证据完整度 | 自动完成或人工复核 | 保守路由 |
| human_review | 草案和风险原因 | 审批结果与备注 | 使用 checkpointer 暂停和恢复 |
| finalize | 已批准状态 | 最终报告 | 不执行设备写操作 |

## 状态设计

图状态保存可序列化的原始数据：触发来源、报警事件、用户问题、测量快照、两阶段检索证据、规则命中、结构化诊断和人工决策。提示词在节点运行时按需组装，避免提示词字符串污染长期状态，也便于模型版本升级。

## 风险闸门

出现以下任一情况时要求人工复核：

- 绝缘、耐压、接地或安全联锁失败。
- 温度、振动或电流达到高风险阈值。
- 建议涉及拆解、重新通电、高能测试或质量放行。
- 关键测量缺失，或候选结论没有足够证据。
- 模型与确定性规则明显冲突。

## 生产部署建议

- API 服务保持无状态，图状态放在 PostgreSQL checkpointer。
- 原始工艺文件进入对象存储，解析文本与元数据进入受控知识索引。
- 向量检索与关键词检索并行，按型号、工位、工艺版本和权限过滤后再重排。
- 数据源凭证放入密钥管理系统，工具使用短时令牌和只读账户。
- 所有写操作使用独立审批流程和幂等键，不能与诊断读取工具混在同一权限域。
